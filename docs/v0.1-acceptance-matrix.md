repeatable command or committed test proves it; implementation alone is not
evidence.

## Phase 2: executor and base blocks

| Area            | Acceptance criterion                                                                                |
| --------------- | --------------------------------------------------------------------------------------------------- |
| Operations      | `file.create`, `dependency.ensure`, `env.ensure`, and `css.ensure` are deterministic and idempotent |
| Recovery        | Failure after the first installer mutation restores installer-owned files                           |
| Conflicts       | Existing user content stops installation without overwrite                                          |
| daisyUI         | Installs only into a verified Fresh Tailwind CSS v4 Vite project                                    |
| Supabase client | Installs into both Tailwind and no-Tailwind Fresh fixtures                                          |
| Repeat install  | A second identical install makes no changes                                                         |
| Manifest        | Installed block version and content hashes are stable and auditable                                 |

## Phase 3: password authentication

| Area            | Acceptance criterion                                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Flows           | Sign in, sign up, sign out, confirmation, forgotten password, password update, and protected account routes exist                           |
| Forms           | Auth forms work without client JavaScript and use POST + 303                                                                                |
| Sessions        | Server clients are request-scoped; v0.1 does not install global session middleware                                                          |
| CSRF            | Cookie-authenticated state-changing routes reject cross-site requests; webhook/machine routes are not accidentally covered                  |
| Cookies         | Multiple existing and Supabase `Set-Cookie` headers all survive response commit                                                             |
| Cache policy    | Supabase private/no-store headers replace an existing public/cacheable policy                                                               |
| Response bodies | Commit rejects `bodyUsed` and locked bodies when auth state is pending                                                                      |
| Response status | Commit rejects every pending response status outside 200 through 599                                                                        |
| Response types  | Redirect, JSON, 204/304, and an unlocked stream follow the documented behavior                                                              |
| Redirects       | Internal path/query/fragment passes; absolute, same-origin absolute, `//`, backslash, control, malformed, and unsafe fallback inputs reject |
| Encoded slash   | The chosen URL-standard behavior is explicit and verified same-origin without repeated decoding                                             |

## Release gate

Before publishing v0.1:

1. every matrix row has linked automated or review evidence;
2. `deno task fmt`, `deno task check`, and `deno task test` pass;
3. the generated example builds from a clean checkout;
4. Windows and Linux integration jobs pass;
5. the final diff has no unexplained deviation from ADR 0001.
