# ADR 0002: evolve the existing CLI for v0.2

- Status: Accepted
- Date: 2026-08-06
- Applies to: `fresh-supabase` v0.2

## Context

Version 0.1 proved the embedded block format, deterministic planner,
stale-plan-resistant executor, recovery journal, audit manifest, JSONC editor,
and Fresh capability inspection. A separate `@fresh-supabase/install` package
would duplicate those security-sensitive components and split the command and
state contracts.

The v0.2 design work also needs to evolve block contents without silently
overwriting user changes. The v0.1 manifest already records block versions and
the resulting hash of every managed target, but the planner intentionally did
not use that state as overwrite permission.

## Decision

### One package and one installer state

Continue to publish only `@fresh-supabase/cli`. Installation remains the `add`
command; no `@fresh-supabase/install` package, second planner, second manifest,
or second recovery protocol will be created.

The existing source layers remain the v0.2 foundation:

- block validation and the closed operation vocabulary;
- catalog and dependency ordering;
- project capability inspection;
- deterministic planning;
- recoverable execution;
- installer manifest and journal;
- comment-preserving JSONC edits.

### Embedded default registry

The default registry remains a generated, embedded snapshot for the first v0.2
increments. Source blocks stay declarative and logically separate from the CLI
engine, while publishing one tested artifact avoids a second network fetch and
keeps a CLI version tied to one immutable block snapshot. A remote registry is
still deferred until block release cadence justifies its additional protocol and
supply-chain surface.

### Fresh scaffold contracts are explicit capabilities

Generated source follows the current Fresh initializer contract instead of
inferring paths from each target file:

- every project-local template import uses the root `@/` alias;
- preflight requires the exact root mapping `"@/": "./"`;
- preflight requires the default `main.ts` to register `staticFiles()` and
  `.fsRoutes()` on the exported `app`, in that order, otherwise generated routes
  would be inert or their island assets would not be served correctly;
- preflight rejects a custom Fresh `serverEntry` or `routeDir`, because v0.2
  inspects `main.ts` and targets `routes/`;
- preflight requires `utils.ts` to export the `define` helper used by routes;
- preflight requires `.gitignore` to explicitly ignore the local root `.env`;
- block templates contain a regression check that rejects relative project
  imports.

These checks are block requirements, not CLI knowledge tied to a particular
block name. A future block that does not use one of these contracts need not
declare the corresponding requirement.

### Fresh-native generated behavior

The password-auth port uses server-rendered native forms and no islands. It
adopts Fresh's `Head` component for route titles, middleware arrays, literal
`FRESH_PUBLIC_*` lookups in browser code, and `ctx.config.basePath` for links,
redirects, callback URLs, and scoped CSRF matching. Tests use the documented
`new App().use(...).get/post(...).handler()` pattern for middleware and helper
behavior, plus a production Vite build and `_fresh/server.js` smoke flow.

Static assets are verified to short-circuit before filesystem route middleware,
and browser environment reads are checked to remain statically analyzable. The
password block owns the root middleware wiring and follows upstream's global
authentication policy: an anonymous request outside `/auth*` and `/login*` is
redirected to `/auth/login`. Installing `client` alone only installs the
reusable middleware helper and does not activate that policy.

The middleware records verified JWT claims in Fresh request state and the
protected route reuses them instead of issuing a second `getUser()` request.
Session-changing server routes must commit the cookie and cache-header changes
collected by the request-scoped adapter; the password block's root middleware
does this centrally, while standalone `client` consumers must call
`commitSupabaseResponse()` themselves. Sign-out intentionally uses `local`
scope, and password length or complexity remains a Supabase project policy
rather than a generated constant.

### Upstream provenance and manual configuration

`password-based-auth` records the current Supabase UI registry item, its
`button`/`card`/`input`/`label` registry dependencies, and the exact 17-source
to 17-target mapping. The Fresh port may distribute those targets across
dependency blocks, but the resolved closure must equal the upstream file list.

Manual Supabase Dashboard and email-template configuration is represented by a
validated `postInstall` string array. The CLI prints this data but cannot
execute it. This keeps the source list aligned with upstream without inventing
extra project files or arbitrary lifecycle hooks.

Supabase CLI also writes Git-ignored runtime sources under `supabase/.temp`.
Because an unscoped `deno check` can still discover them, `client` uses the
declarative `config.exclude.ensure` operation to add `supabase/.temp/**` to the
Deno config without discarding JSONC comments or unrelated formatting.

The release checklist was exercised against a local GoTrue/Postgres/Mailpit
stack. The evidence covers real confirmation and recovery emails, protected
claims, two-session local sign-out, password update, and rejection of the old
password. CI automation of that local stack remains separate from the existing
deterministic mocked and production-build suites.

### Compatible host dependencies

An existing dependency mapping is preserved when the protocol and package name
match and its exact version or caret range is provably contained by the block's
required caret range. Merely intersecting ranges is insufficient. Lower,
broader, differently sourced, or unparseable mappings remain conflicts.

### Multiple requested blocks

`add` accepts one or more block names. The catalog resolves their dependency
union once, preserves deterministic dependency-first ordering, and installs a
shared dependency once. Empty requests, unknown blocks, dependency cycles, and
ambiguous operation ownership fail before writes.

### Managed-file upgrades

Re-running `add` with a newer embedded block may update a `file.create` target
only when all of the following hold:

1. the existing installer manifest is valid;
2. it records the same block and stable operation key;
3. the target path and operation kind still match;
4. the target's current SHA-256 equals the recorded installed hash;
5. the embedded block version is newer than the installed block version.

If the current bytes differ from the recorded hash, the file is user-modified
and remains a conflict. Downgrades are rejected once per block before operations
are inspected, including when a managed file is missing or a block contains only
configuration operations. Configuration operations continue to use semantic
idempotency and conflict rules rather than treating a whole-file hash as
overwrite permission.

### Versioned external contracts

The published block schema version 1 and installer-state schema version 1 are
distinct contextual contracts and remain readable. A future incompatible block
format must use block schema version 2 and adapt into the same internal
operation model; it must not redefine schema version 1. A future incompatible
local state format likewise gets its own explicit state schema migration.

### Transient and durable state

`.fresh-supabase/manifest.json` is durable audit/provenance state and may be
committed. Journals, backups, and temporary files are transient and must be
ignored narrowly; the entire `.fresh-supabase/` directory must not be ignored.

## Initial v0.2 delivery slice

1. bump the package and embedded block versions to `0.2.0`;
2. support dependency-deduplicated multi-block `add` and dry-run;
3. activate hash-guarded upgrades for unmodified `file.create` targets;
4. add tests for upgrade, user drift, downgrade refusal, and multi-block order;
5. retain the v0.1 commands, embedded catalog, and generated runtime behavior.

The authentication-content increment additionally aligns the resolved block
closure to Supabase UI's 17 upstream files and adopts the explicit Fresh
contracts above.

New UI renderers, syntax-aware middleware merge operations, automatic dependency
materialization, remote registries, and block removal are separate v0.2
increments and require their own test-backed changes.

The following ideas from the earlier standalone-installer plan remain deferred
or deliberately different:

- daisyUI remains the renderer for this increment; a `ui-base` renderer is a
  separate block/content decision;
- existing `routes/_middleware.ts` content still conflicts instead of being
  syntax-merged; a generic merge operation needs its own parser and fixtures;
- dependency materialization (`deno install`) and lockfile rollback are not yet
  part of `add`;
- the cookie bridge stays local because it preserves Supabase's `priority`,
  `partitioned`, custom encoding, and cache-header contract beyond the narrower
  `@std/http/cookie` shape; its behavior is covered directly;
- remote registries, source SHA channels, `minFresh`/`minDeno`, and destructive
  force flags are not implied by the embedded v0.2 snapshot.

## Consequences

The project advances without a rewrite or a second public package. Existing v0.1
project state remains useful and becomes the safety proof for managed-file
upgrades. The first v0.2 increment is intentionally infrastructure-focused, so
later authentication and UI changes can be delivered without treating every
existing generated file as either immutable forever or safe to overwrite.
