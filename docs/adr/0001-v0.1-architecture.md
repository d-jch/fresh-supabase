# ADR 0001: v0.1 architecture and scope

- Status: Accepted
- Date: 2026-08-05
- Applies to: `fresh-supabase` v0.1

## Context

Fresh projects need a Fresh-native way to add Supabase capabilities after the
project is created. The tool must support existing projects without taking over
their runtime, silently rewriting application structure, or coupling generated
applications to the installer.

The verified initial compatibility baseline is:

- Deno 2.9.3, released 2026-07-15;
- Fresh and `@fresh/init` 2.3.3, released 2026-04-28;
- Fresh's Vite-based project shape with optional Tailwind CSS v4.

These versions define the first pinned fixture set. They are not an excuse to
depend on `latest`; fixture upgrades must be explicit and reviewed.

## Decision

### Product shape

The repository will publish one JSR package, `@fresh-supabase/cli`. Users create
a project with the official Fresh initializer and run the CLI inside that
project. Generated application code has no runtime dependency on the CLI.

The v0.1 command surface is:

- `doctor`
- `list`
- `view`
- `add`
- `add --dry-run`

The embedded block catalog is:

- `daisyui`
- `supabase-client`
- `password-based-auth`

`password-based-auth` depends on `supabase-client` and `daisyui`.

### Generated application design

Generated code is Fresh-native, Preact-native, and server-first:

- authentication uses ordinary server-rendered forms;
- successful state-changing form submissions use POST followed by a 303;
- islands are added only for interactions that require client-side state;
- daisyUI is the only v0.1 UI renderer;
- CSRF protection is scoped to route groups containing browser
  Cookie-authenticated state-changing handlers.

`supabase-client` does not require Tailwind. `daisyui` and `password-based-auth`
require a verifiable Fresh Tailwind CSS v4 Vite setup. The CLI will not install
or configure Tailwind in v0.1.

### Installer model

Blocks are embedded, declarative data plus templates. The supported operation
families are initially `file.create`, `dependency.ensure`, `env.ensure`, and
`css.ensure`; the exact schema remains draft until Phase 1. Arbitrary
`postInstall` shell hooks are forbidden.

Installation follows this sequence:

1. inspect the target project;
2. detect Fresh capabilities;
3. resolve the block dependency graph;
4. verify every block requirement;
5. detect all file and configuration conflicts;
6. build a complete deterministic plan;
7. write only after all preflight checks pass.

Dry-run stops after step 6 and performs no filesystem, dependency, lockfile, or
manifest mutation. Conflicts stop by default. Installer-owned mutations must be
recoverable when a later write fails, but v0.1 does not claim atomicity for
external or environment-level effects.

Target paths are untrusted. The executor must reject absolute output paths,
parent traversal, symlink escapes, and writes outside the resolved project root.

### Future authentication safety requirements

Phase 3 must implement these already accepted constraints:

- The Supabase server adapter collects every pending `Set-Cookie` value and the
  cache headers supplied by `@supabase/ssr` (`Cache-Control`, `Expires`, and
  `Pragma`) before committing them to a Fresh response.
- Cache headers replace existing cache policy values; `Set-Cookie` values are
  appended and must preserve existing cookies.
- With pending auth changes, response commit rejects a consumed or locked body
  and any status outside 200 through 599. With no pending changes it returns the
  original response unchanged.
- Response commit targets outgoing responses created by application handlers; it
  does not promise to preserve every internal property of arbitrary fetched
  responses.
- Redirect destinations use a path-only policy. They reject absolute URLs,
  network-path references, backslashes, controls, malformed inputs, and unsafe
  fallbacks while preserving valid path/query/fragment values.
- Percent-encoded slashes retain URL-standard path semantics in v0.1; the helper
  must not repeatedly decode them. Tests must prove the emitted URL remains
  same-origin.
- Cookie-authenticated state changes use route-scoped Fresh CSRF middleware.
  Webhooks, machine APIs, and intentionally cross-origin APIs use separate route
  groups and their own authentication model.

### Evidence model

Tests keep three independent sources of evidence:

1. `tests/fixtures/upstream`: exact-version official Fresh initializer output;
2. `tests/fixtures/mutated`: deliberate existing-project and failure shapes;
3. `tests/golden`: human-reviewed expected installation output.

`examples/with-supabase` is generated by this CLI from a pinned official
fixture, then independently checked with build, structure, and auth-flow smoke
tests. A generated example is never the sole oracle for the generator that
created it. Ordinary CI never refreshes fixtures from `latest`.

## Deferred from v0.1

- custom starter or wrapper around the Fresh initializer;
- shadcn compatibility or additional UI renderers;
- remote registry;
- `update` and `remove`;
- global session middleware and `main.ts` AST edits;
- automatic upstream synchronization;
- social authentication, Storage, and Realtime blocks.

## Delivery phases

- Phase 0: repository skeleton, this ADR, acceptance matrix, block-format draft,
  minimal `--help`/`--version` CLI, and test tasks.
- Phase 1: CLI planning commands, block catalog, capability detection, and dry
  run without installation writes.
- Phase 2: recoverable executor plus `daisyui` and `supabase-client`.
- Phase 3: password authentication and its security helpers.
- Phase 4: complete fixtures, golden outputs, example, cross-platform tests, and
  end-to-end verification.

Each phase ends with formatting, type checking, tests, diff review, and an
explicit check for deviations from this ADR before the next phase begins.

## Consequences

The first release stays intentionally narrow and testable. Existing projects
with unusual structures may be rejected when required capabilities cannot be
verified. This is preferable to an unsafe guess or a silent rewrite. More
renderers, lifecycle commands, and global integration can be proposed in later
ADRs after v0.1 installation semantics are proven.
